### 六类角色不是六个固定机构

同一主体可以承担多个角色，但协议必须按角色分别授权、记账和追责。需求方不能同时单独指定 Validator 并控制证据源；Worker 也不能用自己的日志替代独立观测。角色分离的目的不是增加中间商，而是让利益冲突可以被识别。

**结果奖励**支付业务价值，只在结果通过验收后释放。**基础设施费用**支付真实完成的观测、验证、证明和链上终局工作，即使结果正常未达标，这些工作仍然发生。二者混账会让 Validator 有动力无条件投“通过票”，也会让诚实的失败任务无人愿意验证。

### 结果未达标与作弊必须分开

Worker 可能诚实执行却没有达到业务门槛。此时结果奖励退回需求方，但不应自动罚没 Worker；否则执行方只会接受几乎没有不确定性的任务。只有伪造回执、替换输入、重复结算或与 Validator 串谋等可证明违规，才触发保证金罚没。

```text file="settlement-waterfall.txt"
escrow = outcomeReward + validationFee + evidenceFee + chainFee + challengeReserve

accepted: outcomeReward → Worker
rejected: outcomeReward → Requester
fraud:    outcomeReward → Requester; offenderBond → Challenger + SafetyTreasury
```

示例金额用于说明分账关系，不代表协议固定费率。具体市场可以让 Worker 把预期执行成本计入结果报价，也可以单列有上限的执行补贴；无论采用哪种方式，都不能把“调用发生”伪装成“结果已验收”。

### 四个容易写错的地方

1. **Validator 不能按通过票收钱**：验证费应绑定正确完成验收，而不是绑定 `accepted`，否则所有人都有放行激励。
2. **挑战者也要承担成本**：有效反证获得奖励，无效挑战损失保证金，避免用廉价异议拖住所有付款。
3. **保证金要覆盖可获利上限**：只看单次任务奖励不够，还要计算重复作弊、串谋和外部套利收益。
4. **选择机制要限制关联方**：独立抽样、法定人数、身份关联分析和单一运营方权重上限共同提高检测概率。

```text file="incentive-compatibility.txt"
U_cheat = G_cheat - p_detect × (slash + clawback + lostFutureRevenue)

required condition:
U_honest ≥ max(U_cheat, U_collude, U_spamChallenge)
```

经济安全不是一个固定质押数字，而是一组随任务价值、证据质量、验证成本和参与方集中度变化的参数。
