### 确定性状态转换

任务状态可抽象为 `S = (phase, contractRoot, taskTreeRoot, roles, budget, deadlines, nonces)`。节点接收回执 `R` 后先运行验证谓词，再调用状态转换函数。只要序列化、哈希和错误码都规范化，不同节点就能得到相同新根。

```ts file="state-transition.ts"
function apply(state: TaskState, receipt: VerifiedReceipt): TaskState {
  const allowed = TRANSITIONS[state.phase]?.[receipt.kind]
  if (!allowed) throw new Error('invalid phase transition')
  if (receipt.previousStateRoot !== hashState(state)) {
    throw new Error('stale receipt')
  }

  return {
    ...state,
    phase: allowed.next,
    taskTreeRoot: receipt.taskTreeRoot,
    spentNonces: state.spentNonces.add(receipt.nonce),
  }
}
```

前序状态根使回执只能接在指定历史上；nonce 使同一回执不能重复使用；任务树根使阶段转换绑定到真实文件版本。

### 回执的必填绑定

回执不是普通日志。它至少需要引用任务身份、合约版本、前后任务文件根、角色、时效与 nonce，并由对应责任主体签名。若执行使用 TEE、zkML 或外部数据证明，相应证据摘要也应进入签名消息。

```ts file="verify-receipt.ts"
function verifyReceipt(receipt: Receipt, state: TaskState) {
  return receipt.taskId === state.taskId
    && receipt.contractRoot === state.contractRoot
    && receipt.previousTreeRoot === state.taskTreeRoot
    && receipt.expiresAt >= currentBlock()
    && !state.spentNonces.has(receipt.nonce)
    && verifySignerForRole(receipt)
    && verifyMerkleCommitment(receipt.nextTreeRoot, receipt.inclusions)
    && verifyAttachedEvidence(receipt.evidence)
}
```

Merkle Root 证明文件集合没有被替换，不会自动证明文件里的陈述真实。真实性来自签名、证明、数据源核验与 Validator 裁决的组合。

### 乐观验证的安全条件

结果可先进入 `provisional` 状态，并在挑战窗口结束后终局。挑战者必须引用原 `taskId`、有争议的回执根和可复核反证；协议随后选择独立 Validator 或确定性验证器裁决。

安全性同时取决于密码学和经济参数：挑战窗口必须足够长，保证金要覆盖欺骗收益，复核者不能由被挑战方单独选择，错误挑战也要承担成本。否则系统会在“无人愿意挑战”或“恶意挑战阻塞结算”之间失衡。

```text file="dispute-states.txt"
submitted → provisional → finalized → settled
                │
                └→ challenged → upheld  → rejected + slash(worker)
                              └→ denied  → finalized + slash(challenger)
```

### 可用性、稳定性与成本

**可用性**取决于角色冗余和门限。若 `n = 3f + 1` 的 BFT Validator 集需要 `2f + 1` 票，系统只能容忍至多 `f` 个拜占庭故障；Worker 的重试策略不能改变这个安全阈值。

**稳定性**要求任务到达率 `λ` 小于有效服务率 `μ`。模型推理、Validator 复核和挑战处理是不同队列，任何一个长期满足 `λ ≥ μ` 都会形成积压。

**效率**要比较链下执行成本、证据生成成本和全网验证成本。理想情况是 `C_execute + C_prove + n·C_verify` 显著低于 `n·C_execute`，否则“执行一次、多方验证”没有带来系统收益。

这些公式用于检查设计边界，不代表仓库当前的性能。真实参数必须来自实现与基准测试。
