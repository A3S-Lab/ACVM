### 世界状态怎样变化

账户型合约链把协议写成状态转换函数。给定相同前态、交易和区块上下文，所有节点必须算出相同后态：

```text file="state-transition.txt"
UTXO: UTXO_set' = spend(UTXO_set, transaction)
EVM:  S' = EVM(S, transaction, blockContext)
```

外部账户保存 nonce 和余额；合约账户还关联字节码与存储。区块头中的 `stateRoot` 承诺执行完该区块全部交易后的世界状态。节点不接受提议者直接给出的结果，而是按相同顺序执行交易并核对根承诺。

这个模型能表达代币、订单、借贷仓位和治理投票，也带来明确成本：每个验证节点都要重放程序并维护可验证状态。

### 合约不是后台服务

部署交易把字节码写入链上。后续调用携带目标地址、calldata、费用参数和 Gas 上限。EVM 执行完成后得到状态变化、事件日志、返回值和 Gas 用量；失败调用回滚业务状态。

```solidity file="Counter.sol"
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

contract Counter {
    uint256 public value;
    event Incremented(address indexed caller, uint256 nextValue);

    function increment() external {
        value += 1;
        emit Incremented(msg.sender, value);
    }
}
```

验证者会重放 `increment()`。EVM 不能在执行中读取本机文件、调用 HTTP 服务或使用节点自己的时钟，因为这些输入无法保证在所有节点上相同。

资料：[EVM specification](https://ethereum.org/en/developers/docs/evm/)

### 预言机解决输入问题，不保证事实天然可信

如果节点在执行合约时分别请求同一个 API，响应可能因时间、地区、网络故障或服务端状态而不同。协议因此要求外部观察先被签名、聚合或证明，再作为交易输入提交。

```solidity file="PriceConsumer.sol"
function fulfillPrice(uint256 requestId, uint256 price, bytes calldata proof)
    external
{
    require(requestId == pendingRequest, "unexpected request");
    require(oracleRegistry.verify(msg.sender, price, proof), "bad evidence");
    latestPrice = price;
}
```

`verify` 只能检查协议规定的证据。数据源是否可靠、报价是否过期、多少来源构成法定人数以及故障时怎样处理，都属于预言机的信任模型。

</LessonChapter>

### 固定随机种子仍不够

固定种子只能减少采样差异。模型版本、量化方式、GPU 内核、浮点舍入和外部数据快照仍可能改变输出。模型权重和推理成本也不会因固定种子而缩小。

Agent 还会产生不可重复的副作用，例如发送邮件、创建订单、付款或请求人工审批。如果每个验证者都重放这些步骤，同一动作会执行多次。长任务也可能跨越多个区块，无法在单笔交易的 Gas 和时间边界内完成。

适合全网执行的逻辑应继续放在 EVM 或其他确定性 VM 中。模型、API、文件、私密数据和外部副作用则需要链下执行协议。

</LessonChapter>

### 两种状态转换

EVM 把业务计算放进共识执行。每个验证者读取相同前态和交易，执行相同字节码：

```text file="evm-vs-acvm.txt"
EVM:
  S' = EVM(S, tx, blockContext)

ACVM:
  result, evidence = Exec_offchain(intent, frozenEnvironment)
  S' = Apply(S, Verify(receipt, evidence))
```

ACVM 不是“完全不上链”。链上部分仍然确定性执行，并检查：

- 调用者签名、角色权限、nonce、预算和 deadline；
- `contractRoot`、`inputRoot`、`outputRoot` 与前序状态根；
- Validator 裁决、证明或挑战期是否满足协议；
- 当前状态能否接收该回执，以及资产怎样结算。

链下部分负责模型推理、网络请求、文件处理、外部工具和人工审批。每项工作只执行所需次数；验证者复核协议声明的命题，不复制全部副作用。

### zkML 和 TEE 改变的是证据形式

zkML 在链下完成推理和证明生成，链上验证证明；TEE 在受信硬件内执行并签发远程证明；乐观机制先接受结果，在挑战时验证反证。这些方案都没有把大型模型变成由所有共识节点直接重放的 EVM 指令。

小型、确定、可在 Gas 内完成的规则没有必要移出链上。ACVM 处理的是超出这一边界的异步外部工作。

</LessonChapter>

### 五类验证方法

- **重复执行**：多个独立执行者对冻结输入运行确定性任务，比较结果；成本随执行者数量增加。
- **乐观挑战**：结果先进入待确认状态；监控者在挑战期内提交可验证反证，终局时间较长。
- **TEE 远程证明**：证明指定代码在认可的隔离环境内运行；仍需信任硬件、固件和证明服务。
- **zkML**：证明固定电路对承诺输入产生指定输出；数据真实性、模型选择和业务价值不由计算证明覆盖。
- **结果验收**：Validator 按测试集、评分规则或人工判断评估质量；需要防止串谋并提供申诉流程。

“程序按规则执行”“输入来自可靠来源”“输出满足业务目标”是三个命题，证据和故障处理应分别定义。

### 任务状态必须连续

链上只看到最终字符串时，无法判断任务使用了哪份输入、由谁执行、经历了哪些授权以及是否重复结算。状态机把这些条件写入每一次转换。

```ts file="agentic-state-machine.ts"
type TaskState =
  | 'requested'
  | 'assigned'
  | 'running'
  | 'submitted'
  | 'accepted'
  | 'settled'

function applyReceipt(state: TaskState, receipt: VerifiedReceipt): TaskState {
  if (state === 'running' && receipt.kind === 'worker') return 'submitted'
  if (state === 'submitted' && receipt.kind === 'validator') return 'accepted'
  if (state === 'accepted' && receipt.kind === 'settlement') return 'settled'
  throw new Error('receipt is invalid for the current state')
}
```

ACVM 合约模型由此需要四组定义：任务目录、状态转换、角色权限和结算条件。

### 三个命题需要分开验证

1. **计算正确**：指定代码或模型是否对承诺输入产生了该输出。zkML、TEE 证明或重复执行可以覆盖不同强度的计算命题。
2. **来源可信**：输入是否来自约定数据源，版本和时效是否满足 Intent。签名和哈希只能证明绑定关系，不能替代来源治理。
3. **结果合用**：输出是否满足测试集、评分规则、人工审批或现实世界完成条件。这通常需要 Validator、挑战窗口和申诉机制。

```ts file="semantic-acceptance.ts"
function maySettle(task: Task, receipt: Receipt, verdict: Verdict) {
  return verifyExecution(receipt, task.executionPolicy)
    && verifyProvenance(receipt.inputs, task.sourcePolicy)
    && verdict.intentHash === task.intentHash
    && verdict.score >= task.acceptance.minimumScore
    && verdict.challengeWindowClosed
}
```

Worker 回执是待验证声明，不是事实本身。`Intent` 定义目标，Worker 绑定执行记录，Validator 对验收命题签名，结算层只在状态连续且争议条件满足后付款。这样才能把“谁提交了什么”推进到“为什么可以接受这个结果”。
