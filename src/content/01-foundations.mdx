### 签名、验证与排序

Alice 可以用同一私钥签出两笔交易：一笔把 UTXO 支付给 Bob，另一笔支付给 Carol。两份签名都可能正确，但账本只能接受其中一笔。交易有效性和交易顺序因此是两个不同问题。

节点收到交易后检查签名、脚本、UTXO 是否存在以及金额是否守恒。矿工把通过检查的交易写入候选区块。节点对区块重新验证，并按累计工作量选择规范链。任何角色都不能绕过验证规则。

```text file="three-checks.txt"
authorization: signature unlocks the referenced output
validity:      every input exists, is unspent, and preserves value
ordering:      the accepted chain places one conflicting spend first
```

### 节点怎样检查一笔交易

输入通过 `txid:vout` 引用旧输出，并提供满足锁定条件的 witness。输出记录金额和新的锁定条件。节点查询本地 UTXO 集，确认引用存在且尚未花费，再执行脚本和金额检查。

```ts file="verify-transaction.ts"
type Output = { value: bigint; owner: string }
type Input = { prevout: string; signature: Uint8Array }

function verifyTransaction(inputs: Input[], outputs: Output[], fee: bigint) {
  const prevouts = inputs.map(loadUnspentOutput)
  const authorized = inputs.every((input, index) =>
    verifySignature(input, prevouts[index].owner),
  )
  const valueIn = prevouts.reduce((sum, output) => sum + output.value, 0n)
  const valueOut = outputs.reduce((sum, output) => sum + output.value, 0n)

  return authorized && valueIn === valueOut + fee
}
```

实际验证还包括脚本规则、锁定时间、序列号、交易重量和标准性策略。示例保留了 UTXO 查找、授权检查与价值守恒三项基础条件。

### 挖矿概率

区块头被视为 256 位整数。目标值为 `T` 时，单次哈希成功概率近似为：

```text file="pow-probability.txt"
p = Pr[SHA256d(header) ≤ T] = (T + 1) / 2²⁵⁶

Pr[at least one success after k hashes] = 1 - (1 - p)ᵏ

expected block share of miner i ≈ hᵢ / Σh
```

`hᵢ` 是矿工算力，全网算力为 `Σh`。哈希结果无法提前预测，增加算力只会增加单位时间内的试验次数。协议约每 2016 个区块调整目标，使长期平均出块间隔接近十分钟。

有效 PoW 只证明区块头满足目标。区块仍须通过交易、脚本、区块大小和 coinbase 奖励等全部规则；全节点会直接丢弃非法区块。

资料：[Bitcoin white paper](https://bitcoin.org/bitcoin.pdf) · [Bitcoin Developer Guide: Mining](https://developer.bitcoin.org/devguide/mining.html)

### 链选择与概率最终性

节点只在有效区块之间比较 chainwork。区块数量不是准确标准：难度较高的短链可能包含更多累计工作。节点切换到高 chainwork 分支时，会撤销旧分支造成的 UTXO 变化，再按新分支顺序重放交易。

交易之后每增加一个区块，攻击者都要重算目标区块及其后续工作，并追上诚实矿工继续增长的链。回滚概率随确认数下降，但不会在某个固定高度变成严格的零。

### Safety、Liveness 与抗女巫

**Safety** 要求诚实节点不会确认两个冲突状态；**Liveness** 要求网络恢复正常后，新交易仍能继续进入账本。协议必须说明网络时延假设、可容忍的故障类型以及故障上限。

公开网络还要限制一个实体伪造大量身份。PoW 以算力和能源计权，PoS 以可罚没质押计权，PoA 依赖治理认可的身份，DPoS 由持币人选出有限代表。抗女巫机制决定投票权来源，不会自动给出区块排序和最终性。

```ts file="accept-candidate-block.ts"
function acceptCandidate(block: Block, localState: State) {
  if (!membershipRule.accepts(block.proposer)) return false
  if (!proposalRule.accepts(block.header)) return false
  if (!validateEveryTransaction(block, localState)) return false
  return forkChoiceAndFinality.observe(block)
}
```

共识机制的比较单位应当是完整协议，而不是单独比较“谁出块”。

### 提议者和投票者承担不同职责

以太坊把时间分成 12 秒的 slot，32 个 slot 组成一个 epoch。RANDAO 提供协议随机数；每个 slot 选出一名 proposer 构造 beacon block，同时把验证者分配到委员会，对链头和检查点提交 attestation。空 slot 不会停止链，后续 slot 仍可继续出块。

Gasper 组合两套规则：

- **LMD-GHOST** 使用每个验证者最新的有效投票计算当前链头。
- **Casper FFG** 对 epoch 边界的 checkpoint 投票。占总质押量至少 2/3 的 supermajority link 可使检查点 justified；后续检查点满足链接条件后，前一检查点 finalized。

双重提议、双重投票和 surround vote 会触发 slashing。攻击两个冲突终局至少要求约 1/3 质押违反可罚没条件，因此 PoS 的安全成本来自可识别、可销毁的质押。

资料：[Ethereum Proof-of-Stake](https://ethereum.org/en/developers/docs/consensus-mechanisms/pos/) · [Gasper](https://ethereum.org/en/developers/docs/consensus-mechanisms/pos/gasper/) · [Block proposal](https://ethereum.org/en/developers/docs/consensus-mechanisms/pos/block-proposal/)

### Quorum 为什么是 2f+1

验证者总数为 `n = 3f + 1` 时，quorum 大小取 `q = 2f + 1`。任意两个 quorum 的交集至少为 `f + 1`，其中至少有一个诚实节点。诚实节点遵守锁定规则，不会为两个冲突分支同时形成有效证书。

```text file="quorum-intersection.txt"
|Q₁ ∩ Q₂| ≥ |Q₁| + |Q₂| - n
          ≥ (2f + 1) + (2f + 1) - (3f + 1)
          = f + 1
```

HotStuff 按 view 运行。Leader 携带父区块的 QC 提议新区块；副本只为符合安全锁的提议投票；聚合 2f+1 票后生成新 QC。连续的认证链满足提交规则后产生确定性最终性。Leader 失联时，超时证据推动 view change。

HotStuff 的部分同步假设允许网络暂时任意延迟；网络恢复到延迟上界后，正确 Leader 可以继续推动协议。

资料：[HotStuff paper](https://arxiv.org/abs/1803.05069) · [PBFT paper](https://www.usenix.org/conference/osdi-99/practical-byzantine-fault-tolerance)

### 四种常被混在一起的机制

**PoA** 维护授权签名者名单。Clique 采用 in-turn 签名者和随机延迟的 out-of-turn 备用签名者，并限制签名者在最近窗口重复出块。身份治理代替了公开网络的算力或质押准入。

**DPoS** 让持币人投票选出少量 witness 或 producer。入选代表按排班出块，区块何时不可逆则由系统采用的 BFT 投票或确认规则决定。投票集中度和代表串谋属于主要治理风险。

**Raft** 用多数票选 Leader 并复制日志，只处理 crash fault。节点可能恶意签署冲突消息时，Raft 不提供拜占庭安全性。

**PoI** 在 ACVM 设想中把真实需求、执行证据和验收结果折算为贡献。贡献可影响信誉、调度或候选权重，但不能单独决定交易顺序；链仍需 BFT、PoS 或其他最终性协议。

资料：[Clique PoA specification](https://eips.ethereum.org/EIPS/eip-225) · [BitShares DPoS](https://docs.bitshares.org/en/latest/technology/dpos.html) · [Raft paper](https://raft.github.io/raft.pdf)
