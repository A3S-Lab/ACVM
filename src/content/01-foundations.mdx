### 先分清三个问题

Alice 的数字签名只回答“这笔花费是否由 Alice 授权”。如果她同时把同一个输入签给 Bob 和 Carol，两笔交易都可能拥有合法签名。一个去中心化货币还必须解决：**交易是否合法、交易按什么顺序发生、所有节点最终接受哪一份历史**。

比特币的关键不是把账本复制很多份，而是让每个节点按同一套规则独立验证，再让工作量证明为候选历史赋予可比较的现实成本。共识选择的是“累计工作量最多的有效链”，而不是盲信最长、最快或节点最多的链。

> 本章心智模型：密码学负责授权，共识负责排序，经济成本负责让历史难以改写。

### 钱包实际构造了什么

UTXO 是一笔旧交易中尚未花费的输出。交易输入引用旧输出的 `txid` 与索引，并提供满足锁定脚本的见证；输出则写入新的金额与花费条件。节点验证时不需要查询某个“账户余额”，只需确认引用存在、尚未花费、见证有效且价值守恒。

```ts file="verify-transaction.ts"
type Output = { value: bigint; owner: string }
type Input = { prevout: string; signature: Uint8Array }

function verifyTransaction(inputs: Input[], outputs: Output[], fee: bigint) {
  const prevouts = inputs.map(loadUnspentOutput)
  const authorizationOk = inputs.every((input, index) =>
    verifySignature(input, prevouts[index].owner),
  )
  const valueIn = prevouts.reduce((sum, output) => sum + output.value, 0n)
  const valueOut = outputs.reduce((sum, output) => sum + output.value, 0n)

  return authorizationOk && valueIn === valueOut + fee
}
```

这里故意省略了脚本、锁定时间、序列号等细节，但保留了全节点最核心的三项检查：**来源未花费、授权成立、输入等于输出加手续费**。

### 区块头为什么足够重要

区块头把前一区块哈希、交易集合的 Merkle Root、时间、难度目标和 nonce 绑定在一起。修改任何一笔交易都会改变 Merkle Root，继而改变区块哈希以及之后整条链的引用。

```text file="block-header.txt"
version | previousBlockHash | merkleRoot | time | target | nonce

valid(block) := validateAllTransactions(block)
             && hash(block.header) < target
```

PoW 证明矿工为这个候选区块搜索过稀缺的哈希结果；它**不证明区块里的交易正确**。每个全节点仍会完整验证区块，非法区块即使拥有巨大算力也会被拒绝。

### 最终性不是一个瞬间

网络传播存在延迟，两个矿工可能基于同一父块同时找到新区块。节点先接受自己看到的有效链尖；当某一分支累积更多工作量时，节点会回滚落败分支的状态并重放胜出分支，这就是重组。

确认数不是中央机构发出的“批准”，而是目标交易之后又叠加了多少区块工作量。交易越深，攻击者从它之前分叉并追上诚实链所需的预期成本越高。

### 从验证花费到执行状态转换

以太坊把协议抽象成状态转换函数 `S′ = Υ(S, T)`：给定同一个前态 `S` 和同一笔交易 `T`，所有节点必须得到相同后态 `S′`。外部账户保存 nonce 与余额；合约账户还保存代码哈希和存储根。

这一步演化的意义是：状态不再只回答“哪些价值可以被花费”，还可以记录订单、投票、借贷仓位和其他长期程序变量。但代价也随之出现——每个验证节点都必须重放程序并保存可验证状态。

```text file="state-transition.txt"
Bitcoin:  UTXO_set' = spend(UTXO_set, transaction)
Ethereum: worldState' = EVM(worldState, transaction, blockContext)
```

### 合约不是后台服务

Solidity 代码部署后成为链上的 EVM 字节码。交易携带目标地址、调用数据和 Gas 上限；EVM 使用栈、内存和持久存储执行指令。执行产生的新状态、日志与 Gas 消耗进入交易回执。

```solidity file="Counter.sol"
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

contract Counter {
    uint256 public value;
    event Incremented(address indexed caller, uint256 nextValue);

    function increment() external {
        value += 1;
        emit Incremented(msg.sender, value);
    }
}
```

所有验证者都会重放 `increment()`；任何依赖本机时间、随机文件或 HTTP 响应的行为都可能让节点得到不同结果，因此这些能力不属于 EVM 的共识执行环境。

</LessonChapter>

### 一笔调用经过五层检查

钱包先用账户 nonce 防重放，并对交易签名。节点检查签名、nonce、费用字段和余额后才把它放入交易池。区块提议者决定排序；EVM 执行时逐条扣除 Gas；最后回执记录成功状态、累计 Gas 和事件日志。

```ts file="transaction-envelope.ts"
const transaction = {

  nonce: 42n,

```

### 预言机问题本质上是验证问题

如果每个节点在执行交易时各自请求天气 API，它们可能因为时间、网络或服务端差异得到不同答案，共识会立即分裂。因此外部观察必须先变成一笔链上输入，然后由合约按确定性规则处理。

```solidity file="PriceConsumer.sol"
function fulfillPrice(uint256 requestId, uint256 price, bytes calldata proof)
    external
{
    require(requestId == pendingRequest, "unexpected request");
    require(oracleRegistry.verify(msg.sender, price, proof), "bad evidence");
    latestPrice = price;
}
```

这里的 `verify` 只能检查协议定义的证据。它不能魔法般保证数据源诚实；来源、时效、聚合方式、失败回退和争议路径都属于系统的显式信任模型。

</LessonChapter>

### 共识不应该复制昂贵智能

大模型推理可能需要 GPU、数十秒到数小时、私有输入和外部工具。即使固定随机种子，不同算子、量化版本或硬件也可能产生细微差异。让所有节点重做一次，会把单次 AI 成本乘以验证者数量。

正确的问题不是“怎样把模型塞进 EVM”，而是“链上最少需要验证哪些事实，才能安全地接受链下结果”。答案通常包括任务授权、输入输出承诺、代码或模型版本、执行证据、验收裁决和防重放字段。

> 区块链保存的是可达成共识的承诺与状态，不必保存每次计算的全部过程和明文。

### 把一次 API 调用拆成协议

请求阶段冻结目标和验收条件；Worker 只负责产生结果与执行回执；Validator 按独立规则检查；链上逻辑只接受满足签名、根承诺、证明和状态前置条件的回执。各方不能用一个裸字符串“成功”替代证据。

```ts file="task-receipt.ts"
type TaskReceipt = {
  taskId: string
  intentHash: `0x${string}`
  inputRoot: `0x${string}`
  outputRoot: `0x${string}`
  codeHash: `0x${string}`
  nonce: bigint
  workerSignature: `0x${string}`
  validatorVerdict?: 'accepted' | 'rejected'
}

function canSettle(receipt: TaskReceipt, state: TaskState) {
  return state.taskId === receipt.taskId
    && state.inputRoot === receipt.inputRoot
    && !state.spentNonces.has(receipt.nonce)
    && receipt.validatorVerdict === 'accepted'
}
```

### 先写命题，再选证明

- **重复执行**适合便宜、确定的任务，证明多个独立执行者得到相同结果。
- **乐观挑战**先暂定接受，适合可以在争议时重放或提交反证的任务。
- **TEE 远程证明**说明指定代码在被认可的隔离硬件中运行过，但仍信任硬件供应链。
- **zkML**证明固定电路对承诺输入产生了该输出，但证明成本、支持算子和数据真实性仍是边界。
- **结果验收**判断输出是否达到业务目标，适合主观或开放式任务，但必须治理 Validator 串谋。

好的设计会把“执行正确”“数据来自哪里”“结果是否有用”分别建模，然后按风险组合证据、保证金、挑战期和人工复核，而不是把它们混成一句“AI 已验证”。

</LessonChapter>

### 原子交易不够表达 Agent 工作

智能合约的典型调用在一笔交易里成功或回滚；Agent 任务却可能等待外部数据、调用多个工具、跨越审批、暂停重试并委托其他 Agent。把这些过程隐藏在一个中心化服务里，链上只看到最终返回值，就失去了责任与状态连续性。

```ts file="agentic-state-machine.ts"
type TaskState =
  | 'requested'
  | 'assigned'
  | 'running'
  | 'submitted'
  | 'accepted'
  | 'settled'

function applyReceipt(state: TaskState, receipt: VerifiedReceipt): TaskState {
  if (state === 'running' && receipt.kind === 'worker') return 'submitted'
  if (state === 'submitted' && receipt.kind === 'validator') return 'accepted'
  if (state === 'accepted' && receipt.kind === 'settlement') return 'settled'
  throw new Error('receipt is invalid for the current state')
}
```

这就是进入 ACVM 的桥：**链下执行可以异步和复杂，链上状态转换必须简单、确定、可验证**。下一部分开始定义任务目录、状态机、回执和争议协议。
